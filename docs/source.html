Executable: run it locally

CRKL-Space runs as three services: a MySQL 8.0 database with our sample data, a FastAPI backend, and a Next.js frontend. Docker Compose builds and starts all three with one command, so you don't need to install MySQL, Python, or Node.js.

What you need

  • Docker Desktop (macOS, Windows, or Linux), running before you start.
  • Git, or download the code as a ZIP file from GitHub instead.
  • Port 3000 free on your computer. It's the only port CRKL-Space uses.
  • An internet connection the first time, to download the MySQL, Python, and Node.js images.

1. Get the code

Clone the repository and open its folder:

git clone https://github.com/CRKL-SDSU/CRKL.git
cd CRKL

Or, on GitHub, click Code → Download ZIP, unzip it, and open the folder in a terminal.

2. Configure

The .env file

The only file you need to create is .env, which holds the two database passwords. Copy the example in the CRKL folder:

cp .env.example .env

On Windows (Command Prompt), use copy .env.example .env. Then open .env in a text editor and replace both placeholder values (change-me-root and change-me-app) with passwords of your own choice. These are new passwords for the database Docker creates on your computer, not existing accounts, so any values work:

SettingWhat it isExample
CRKL_DB_ROOT_PASSWORDPassword for MySQL's root account. Used only on the first start, to create the database and the application user.root-secret-123
CRKL_DB_USER_PASSWORDPassword for crkl, the account the backend uses. It can only read and write rows in crkl_db; it can't drop tables or change the schema.app-secret-456
  • Choose any values, but don't use single quotes (') in them.
  • Docker refuses to start if either value is missing, so you can't accidentally run with an empty password.
  • The passwords are applied only on the first start. To change them later, reset the database (see Stop and reset).
  • .env is ignored by Git, so your passwords are never committed.

Other configuration files

These are already set up for Docker. You don't need to edit them.

FileWhat it configures
docker-compose.yamlThe three services, the order they start in, and the one published port (3000). The backend and database are reachable only inside Docker.
backend/conf/docker.yamlHow the backend connects to MySQL: host mysql, port 3306, user crkl, database crkl_db. The password comes from CRKL_DB_USER_PASSWORD in .env.
specs/db/DDL.sql, specs/db/dummy_data.sql, docker/mysql/03-app-user.shRun by MySQL on the first start, in this order: create the tables, load the sample data, and create the crkl user.

3. Start

In the CRKL folder, run:

docker compose up --build

The first start takes a few minutes. Docker downloads the images, builds the backend and frontend, and MySQL creates the database and loads the sample data. Each service waits until the one before it is healthy:

  1. mysql starts and finishes loading the data.
  2. backend starts once it can log in to MySQL as crkl.
  3. frontend starts once the backend reports the database as connected.

Leave this terminal open; the logs of all three services appear in it. Later starts are much faster, because the images and data are kept.

4. Check that it works

  1. Open http://localhost:3000/explore.
  2. With Missions selected and Include related records checked, search for NASA.
  3. You should see 28 results. Uncheck Include related records and search again: 0 results, because no mission mentions NASA in its own fields.

See the Instructions for everything else you can do on the Explore page.

5. Stop and reset

To…Run
Stop the services (data is kept)Press Ctrl+C in the terminal, then docker compose down
Start againdocker compose up
Reset the database to the sample data (also applies new passwords from .env)docker compose down -v, then docker compose up

Troubleshooting

ProblemWhat to do
Cannot connect to the Docker daemonDocker Desktop isn't running. Start it, wait until it says it's running, and try again.
set CRKL_DB_ROOT_PASSWORD in .env (or …USER_PASSWORD…)The .env file is missing or a value is empty. Repeat step 2 in the CRKL folder.
port is already allocated for 3000Another program is using port 3000. Stop it, then run docker compose up again.
The backend never becomes healthy after you changed the passwordsThe database still has the old passwords from its first start. Run docker compose down -v, then docker compose up.
The page shows API returned 502 or 503The backend or database isn't ready yet, or has stopped. Check the terminal logs, wait a moment, and reload.

Running without Docker

For development, you can also run each service directly with Homebrew MySQL 8.0, Python 3.12, and Node.js 20. See “B. Local (without Docker)” in the README.

AI usage

How we used AI

We used AI coding assistants openly throughout development, as allowed by the CS 514 AI policy: GitHub Copilot and Claude Code. Most of the AI-assisted work was in the implementation: the basic API endpoints, the Next.js proxy, tests, the CI/CD pipeline, the Docker setup, and documentation. Some parts were written by hand: Ryan wrote the backend skeleton, Lia built the website and our first screens, and Kazuhiro extended the API endpoints and wrote the SQL and features such as the Include related records option and the attributes shown on search result cards.

How much

We didn't measure an exact percentage. Roughly, AI assisted with large parts of the implementation, while the data model, the API design, and the architecture were our own decisions.

What the team decided, and what AI did

We decided the what and the why; AI mostly helped with the how. Our decisions included:

  • basing our data model on Launch Library 2;
  • cutting the original design down to four core entities connected through junction tables;
  • keeping the backend and database private behind a Next.js proxy; and
  • running search in MySQL so related records can be matched with joins.

AI did not design our database. We studied the Launch Library 2 API, chose which entities to keep, and decided to model the relationships as many-to-many with junction tables. AI helped us write it up (the DDL, the ER diagram, the documentation), but every table and key is something we can explain and defend.

How we worked with AI

We worked spec-first. We wrote the OpenAPI specification and the database schema first, gave them to the AI as context, and asked it how to implement one small feature at a time.

How we checked AI output

  1. A written spec: the code has to match the OpenAPI specification and the DDL.
  2. Automated tests: backend and frontend tests, a type check, and a production build run in GitHub Actions on every push.
  3. Pull requests: code changes are reviewed in a pull request before they are merged.
  4. The real database: we ran queries against MySQL and checked with EXPLAIN that related search uses the junction tables' composite primary keys.

How we modified and extended AI output

  • We reviewed and corrected AI-written documentation for accuracy and clarity.
  • We made the design decisions ourselves and replaced AI suggestions that didn't fit our constraints (for example, how we keep source IDs unique across data sources).
  • We replaced or extended AI-generated code with our own features or endpoints (for example, related-record search over the junction tables).
  • We scoped AI drafts down to a design we could build, normalize, and explain (for example, reducing an oversized schema to four core entities).

About AI co-authors in our Git history

Git operations (commits, branches, pushes, pull requests) were run through AI tools as a matter of habit, including for changes written by hand. A Co-authored-by trailer shows that a commit was made through an AI tool, not that the AI wrote its content.

The demo video and sample data

  • Demo video: we automated the screen recording with a short Puppeteer script, written with Claude Code. The app and the results in the video are real: it is a recording of CRKL-Space running locally against MySQL, not edited or sped up. The cursor and click highlights were added by the script for visibility.
  • Sample data: the Phase 1 records are sample data in the Launch Library 2 format (for example, "Lunar South Pole Habitation Scout" is not a real mission). We generated them with AI to get a realistic volume quickly.

What we learned

AI is fast, but only as good as the spec you give it. When our requirements were vague, it produced code that looked right but didn't fit. Writing the OpenAPI specification and the DDL first made its output much more reliable. We still read and understand every line, because we are responsible for it.
